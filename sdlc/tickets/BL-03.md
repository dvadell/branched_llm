title: Cleanup leftovers + configurable timeout on the synchronous Chat API
----

Two small but real rough edges for downstream consumers (notably `soundai`):

## Scope

### 1. Remove the `:cara` leftover in `ChatClient.default_model/0`

`lib/branched_llm/chat_client.ex` line ~85 reads:

```elixir
Application.get_env(:cara, :ai_model) ||
  Application.get_env(:branched_llm, :ai_model, "ollama:cara-cpu")
```

The `:cara` app is a previous incarnation of this project and no longer exists.
Reading it produces a compile/runtime warning for consumers and is dead config.
Replace with a single lookup under `:branched_llm`:

```elixir
Application.get_env(:branched_llm, :ai_model, "ollama:cara-cpu")
```

Update the module docs (`Chat`, `ChatClient`, `BranchedLLM`, README, guides) if
they mention `:cara`. Bump the fallback model string to something neutral, e.g.
`"openai:gpt-4o-mini"`, or keep the current value — decide and document.

### 2. Configurable timeout on `Chat.send_message/3`

`Chat.send_message/3` blocks in `wait_for_sync_result/4` with a hard-coded
`60_000` ms `after` (two clauses). Web apps need to budget the HTTP request
time and fail fast with a friendly message.

- Accept a `:timeout` option (milliseconds, default `60_000`) in `send_message/3`
  and thread it into both `wait_for_sync_result` clauses.
- On timeout keep returning `{:error, "Timed out waiting for LLM response"}`
  (include the timeout value for debuggability).
- Document the option in the `@doc` and the README Quick Start.

Also verify the timeout is actually honored end-to-end: the orchestrator's
outer `retry` loop (10 attempts) runs inside the task, and the sync caller only
waits on `{:llm_end, ...}` / `{:llm_error, ...}`; a slow/never-responding
provider should surface as a timeout within the requested budget, not 60 s.

### 3. Consistency

- Grep the repo for other hard-coded `60_000` / `:cara` references and address
  them (e.g. README examples, `guides/`, tests that assert the 60 s value).
