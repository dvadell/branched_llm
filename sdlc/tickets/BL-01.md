----
title: Fix the 2 failing wire-protocol e2e tests (empty request body)
----

`test/e2e/wire_protocol_test.exs` currently fails both its tests on a clean
`MIX_ENV=test mix test` (86 tests, 2 failures):

1. `wire protocol — bypass only schema path — sends response_format in HTTP request body`
2. `wire protocol — bypass only non-schema path — does NOT send response_format in HTTP request body`

Both fail with `No request body received` because the helper that captures the
request body crashes first with a `Jason.DecodeError` ("unexpected end of input
at position 0") — the request body read inside the Bypass handler is empty.

## Symptom

```text
** (Jason.DecodeError) unexpected end of input at position 0
    (branched_llm 0.2.1) test/support/e2e_test_case.ex:178: anonymous fn/4
      in BranchedLLM.E2E.TestCase.expect_and_inspect_sse/2
```

i.e. `Conn.read_body(conn)` in `expect_and_inspect_sse/2` returns an empty body
for the `POST /v1/chat/completions` request, so `Jason.decode!` blows up before
the `{:request_body, body}` message is sent, and `get_request_body/1` times out.

## Root cause

The outgoing `POST /v1/chat/completions` request was sent with **no body at all**
(no `content-length`, no `transfer-encoding`; the Bypass handler saw an empty
body and `Conn.read_body/2` returned `{:ok, "", conn}`), so `Jason.decode!`
crashed with "unexpected end of input at position 0".

Capturing the request headers/body against a local Bypass showed exactly:

```
REQ HEADERS: %{"accept" => "text/event-stream", "content-type" => "application/json",
               "host" => "localhost:40355", "user-agent" => "mint/1.8.0"}
REQ BODY: ""
```

The request is built by `ReqLLM.Providers.Ollama.attach_stream/4`, which calls
`encode_stream_body/3` → `request |> encode_body() |> Map.fetch!(:body)`. The
provider's `encode_body/1` (from `ReqLLM.Provider.Defaults.encode_body_from_map/2`)
only sets `request.options[:json]` — the actual `:body` field is populated later
by Req's `Req.Steps.encode_body` pipeline step, which never runs in the streaming
path. So `Map.fetch!(:body)` returned `nil`, and `Finch.build(:post, url,
headers, nil)` sent an empty request.

This was an upstream `req_llm` bug. branched_llm pinned `{:req_llm, "~> 1.13.0"}`
(May 2026), which predates the upstream fixes:

- `req_llm` v1.17.0: "ollama: provider sent an empty request body
  (Content-Length: 0) → Ollama 400 EOF (#782)"
- `req_llm` v1.17.1: "ollama: streaming provider also sent an empty request body"

## Fix

Bump `req_llm` to `~> 1.17.1` (resolved `1.13.0 → 1.17.1`) in `mix.exs`. This
pulls in the Ollama streaming body fixes plus ~3 months of bug fixes from the
1.14–1.17 releases, with no changes required in branched_llm's own code.

One side-effect: `req_llm` 1.17.x dropped `uniq` from its dependency list, so
`Uniq.UUID` was no longer compiled before branched_llm, producing a
`Uniq.UUID.uuid4/0 is undefined` warning that broke `mix compile
--warnings-as-errors` (part of `mix precommit`). branched_llm calls `Uniq.UUID`
directly in `lib/branched_llm/uuid.ex`, so `{:uniq, "~> 0.6"}` was added as a
direct dependency.

The test helper (`expect_and_inspect_sse/2`) did not need changes — with a real
body on the wire, `Conn.read_body/2` returns the JSON and the two assertions
still verify `response_format` presence (schema path) / absence (non-schema
path).
